Why the 0.43.0 release's signing step compiled atm-app with the secrets in its environment, and the fix. **This changes the release workflow, so it needs your yes**: approving this review is that yes.

**Cause (reproduced locally):** atm-app's build script (tauri-build) watches `app/src-tauri/permissions/` (`rerun-if-changed`), and writes `permissions/autogenerated/*.toml` into it while it runs. These are generated and not committed, so a fresh checkout like CI's doesn't have them. The first compile writes them *after* the build script's recorded start time, so Cargo sees them as newer and the next compile of that architecture recompiles atm-app once. In CI, the no-secrets step compiled aarch64 first (writing the files), then x86_64 (already newer than the files, so up to date afterwards). The signing step then recompiled aarch64 only: 3 m 11 s, as the log shows.
- Locally, after deleting `permissions/`, three builds in a row: the 1st and 2nd compile atm-app, the 3rd compiles nothing.
- Not the secrets or the config: two builds in a row with dummy `APPLE_*`/`TAURI_SIGNING_*` set, and two universal builds, compiled nothing the second time while `permissions/` existed.

**Fix (`release.yml`):**
- The no-secrets step repeats the compile, at most 3 passes, until a pass's output has no `Compiling`. It fails if the 3rd still compiles.
- The signing step tees its output and fails if it says `Compiling` (removing the notary key first), so a compile with the secrets can't go unnoticed again.
- I left the generated files uncommitted, as `app/src-tauri/.gitignore` says they're never committed. Committing them would also fix it, but they'd go stale with each new command.

Tests: `ci-workflow.test.ts` checks the passes and the signing step's check. The security doc's §"Secrets kept from what compiles" notes the change. The real test is the next release's log: no `Compiling` in the signing step.
